# /design — PT Career 디자인 작업 흐름

사용자는 디자인·개발 비전문가다. 모든 설명은 쉬운 말로, 전문 용어에는 괄호로 쉬운 뜻을 붙인다.
예) "대비(글자와 배경의 밝기 차이)", "토큰(사이트 전체 공통 디자인 값)".

## 기준 파일

- 디자인 토큰: `app/globals.css` 의 `@theme` 블록 한 곳. 색·글꼴·글자 크기·여백·모서리·그림자 모두 여기서 관리.
  - Tailwind v4라 `tailwind.config.ts` 는 쓰지 않는다.
  - 사이트 대부분은 Tailwind 기본 팔레트(`gray-*`, `blue-*`)와 기본 스케일(`rounded-lg`, `p-4`)을 쓴다. 이것도 토큰이다. 사이트 전체에 걸친 변경은 `@theme` 에서 해당 변수(예: `--color-blue-600`, `--radius-lg`, `--text-sm`)를 덮어써서 한 번에 반영한다.
  - 특정 화면/부품 하나만 바꿀 때는 그 컴포넌트의 클래스만 고친다. 새 임의값(`text-[13px]`, `bg-[#123456]`)은 만들지 말고, 필요하면 `@theme` 에 이름 붙은 토큰을 추가한 뒤 쓴다.
- 개발 서버: `.claude/launch.json` 의 `pt-career-web-dev` (localhost:3000, 저장하면 화면 즉시 갱신).
- 사이트는 라이트 모드 전용(`app/layout.tsx` 의 `colorScheme: "light"`).

## 절대 규칙

1. 디자인 외 코드는 건드리지 않는다: 데이터 조회, 서버 액션(`app/actions`), API, `lib/`, `supabase/`, `middleware.ts`, DB, 폼 검증·저장 로직. 바꿔도 되는 것은 클래스명(className), `app/globals.css`, 순수 표시용 마크업(문구 배치, 아이콘, 장식 요소)뿐. 애매하면 바꾸기 전에 묻는다.
2. 한 번에 한 가지만 바꾼다. 지시에 여러 요청이 섞이면 목록으로 나눠 보여주고 첫 번째부터 하나씩 진행한다.
3. `main` 에 직접 커밋·푸시하지 않는다. 사용자가 "메인 반영"이라고 말하기 전에는 절대 병합하지 않는다.
4. 지시가 디자인 원칙상 나쁘면(글자 대비 부족, 누르기 어려운 크기 44px 미만, 브랜드 일관성 훼손, 정보가 안 읽힘 등) 그대로 따르지 말고, 먼저 이유와 대안을 쉬운 말로 제시하고 사용자 선택을 기다린다.
5. 사이트 주소(레퍼런스)를 받으면 브라우저 패널로 열어 색·여백·글꼴·톤(분위기)을 분석해 표로 요약한 뒤, 그 분석을 시안에 반영한다. 레퍼런스의 로고·이미지·문구를 복사하지 않는다.

## 흐름

### 1단계 — 지시 이해와 시안 제시

1. 작업 트리가 깨끗한지 확인(`git status`). 남은 변경이 있으면 사용자에게 알리고 멈춘다.
2. 지시가 가리키는 화면·부품을 코드와 브라우저 패널에서 찾는다. 대상이 애매하면 후보를 보여주고 묻는다.
3. 시안 2~3개를 제시한다. 형식:

   **시안 A (추천)** — 무엇이 바뀌는지 한 줄
   - 좋은 점: 한 줄
   - 아쉬운 점: 한 줄

   시안끼리는 방향이 확실히 달라야 한다(예: 색만 진하게 / 모양을 바꿈 / 크기·여백을 바꿈). 가능하면 각 시안을 브라우저 패널에서 임시로 적용해 스크린샷으로 보여준 뒤 원래대로 돌려놓는다(파일 변경은 선택 전까지 남기지 않는다).
4. 사용자의 선택을 기다린다.

### 2단계 — 적용과 미리보기

1. 최신 main에서 작업 브랜치를 만든다:
   `git fetch origin` → `git switch -c design/<영문-짧은-설명> origin/main` → `git branch --unset-upstream` (실수로 main에 푸시되는 것 방지).
2. 적용 **전** 스크린샷: 데스크톱 1장 + 모바일(375px, `resize_window` 로 width 375) 1장.
3. 선택한 시안을 적용한다(토큰 우선).
4. 적용 **후** 같은 화면을 데스크톱·모바일(375px) 스크린샷으로 찍고, 전/후를 나란히 보여준다. 끝나면 `resize_window` preset `desktop` 으로 되돌린다.

### 3단계 — 승인 전 자동 점검 (결과를 ✅/⚠️ 목록으로 보고)

- 글자 대비 (WCAG AA): 바뀐 요소의 글자색·배경색을 `javascript_tool` 로 계산된 값(getComputedStyle)에서 읽어 대비율을 계산. 일반 글자 4.5:1 이상, 큰 글자(24px 이상 또는 굵은 18.66px 이상) 3:1 이상.
- 모바일 화면 깨짐: 375px에서 `document.documentElement.scrollWidth > innerWidth` 가 아닌지(가로 스크롤 없음), 글자 잘림·겹침이 없는지 스크린샷으로 확인. 누르는 요소는 44px 이상.
- 다크모드: `resize_window` 의 `colorScheme: "dark"` 로 열어 화면이 그대로 밝은 테마로 정상 표시되는지(글자가 사라지거나 배경이 어두워지지 않는지) 확인 후 light로 복구. 사이트는 라이트 전용이므로 "다크 기기에서도 깨지지 않음"이 통과 기준.
- 콘솔 에러: `read_console_messages` (onlyErrors) 와 `preview_logs` (level error). 이번 변경과 무관한 기존 에러는 구분해서 알린다.

⚠️ 항목이 있으면 고치는 방법을 제안하고, 사용자가 원하면 고친 뒤 다시 점검한다.

### 4단계 — 명령어

- **"승인"**: 바뀐 파일만 `git add` → 커밋 → `git push -u origin <design/브랜치>`. 커밋 메시지는 한국어 일상 언어로:
  ```
  design: 메인 버튼을 더 진한 파란색으로

  왜: 버튼이 배경에 묻혀 눈에 덜 띈다는 의견. 더 진한 색으로 신뢰감과 눈에 띄는 정도를 높였다.
  무엇: 브랜드 버튼 색 blue-600 → blue-700 (globals.css 토큰)
  점검: 글자 대비 6.7:1 (AA 통과), 모바일 375px 정상, 콘솔 에러 없음
  ```
  푸시 후 Vercel 미리보기 링크를 찾아 알려준다: Vercel MCP `list_deployments`(해당 브랜치의 최신 배포 URL) 또는 PR이 있으면 `gh pr checks`. 빌드 중이면 완료까지 기다렸다가 링크를 준다. 링크를 못 찾으면 그렇다고 말한다(지어내지 않는다).
- **"메인 반영"**: 해당 design/ 브랜치로 PR을 만들고(`gh pr create --base main`, 설명은 쉬운 말로), 사용자에게 PR 링크를 보여준 뒤 병합(`gh pr merge --merge`). main에 로컬에서 직접 push 하지 않는다. 병합 후 운영 배포 상태를 알려준다.
- **"되돌려"**: 직전 디자인 커밋을 `git revert --no-edit <커밋>` 으로 되돌린다(기록을 지우지 않고 '취소 커밋'을 새로 만듦). 이미 푸시된 브랜치면 되돌린 커밋도 푸시. 이미 main에 반영된 변경이면 main에 직접 하지 말고, 새 design/revert-… 브랜치에서 revert 후 위 "승인"→"메인 반영" 흐름을 따른다. 되돌린 뒤 브라우저 패널에서 원래 모습으로 돌아왔는지 스크린샷으로 보여준다.

## 말투

- 결과 보고는 짧게: 무엇을 바꿨는지 → 스크린샷 → 점검 결과 → 다음에 할 수 있는 말("승인" / "되돌려" / 다른 시안).
- 코드 diff를 그대로 보여주지 말고 "버튼 색: 파랑(보통) → 파랑(진함)"처럼 풀어서 설명한다.
