# 보안 작업 원칙

확정일: 2026-11-03 KST · 사용자 요청 · PT Career 전체 작업에 적용

## 비밀값 취급
- Supabase 서버키, Google API/OAuth/서비스 계정 비밀값, JWT 서명키, DB 비밀번호, 인증 토큰은 비밀정보다. 설정 이름·대상·상태와 원문을 구분한다.
- 원문을 불필요하게 조회하거나 채팅·터미널 표준 출력/오류·운영/빌드 로그·스크린샷·Git·문서·현황판·배포 산출물에 남기지 않는다. 실제 비밀값으로 만든 오류 예시도 재사용하지 않는다.
- 서버용 키는 클라이언트 코드, NEXT_PUBLIC_ 변수, 공개 API 응답에 넣지 않는다. 로그인 정보·민감한 개인정보·전체 요청 헤더/환경변수도 출력하지 않는다.
- 보호된 설정 도구나 값을 출력하지 않는 승인된 비밀 입력 경로를 사용한다. 안전한 경로를 확보하지 못하면 구현·입력 위치·검증 절차를 준비하고 비밀값 입력만 사용자에게 맡긴다. 채팅에 키를 붙여 달라고 요구하지 않는다.
- 승인된 도구가 발급한 일회성 작업 자격은 해당 목적·범위에서만 메모리로 취급하고 보호된 입력으로 전달한다. 실제 애플리케이션 키를 명령 출력으로 꺼내 다른 도구에 옮기는 방식은 사용하지 않는다.

## 권한과 변경 승인
- 코드 수정, 사용처/영향 분석, 가짜 값 테스트, 공개 설정 확인과 배포 검증을 먼저 준비한다.
- 키 신규 발급·교체/폐기, 권한 확대, 인증 방식·데이터 공개 범위 변경은 대상·권한·영향·복구 방법을 확인하고 구체적으로 승인된 범위에서만 진행한다. 일반 배포 요청이나 설명 질문을 이런 변경의 포괄 승인으로 해석하지 않는다.
- 같은 범위가 이미 명시적으로 승인된 경우 승인 요청을 반복하지 않는다. 범위 확대나 예상하지 못한 영향이 생기면 다시 확인한다.
- DB·Storage는 최소 권한과 실제 소유자/관리자 검증을 유지한다. UI 숨김만으로 접근을 제한했다고 판단하지 않는다. 운영 자료 삭제·공개 확대·타인 데이터 변경을 진단 편의로 수행하지 않는다.
- Supabase와 Google의 키 종류·사용처·교체 영향은 각각 확인한다. 비공개 로그도 안전한 비밀 보관소로 취급하지 않는다.

## 진단과 검증
- SDK 오류 전체·message·stack·요청 객체·헤더·환경변수를 그대로 기록하지 않는다. 통제된 오류 분류/코드와 비밀값을 포함하지 않는 최소 문맥만 남긴다. 오류 코드 자체도 비밀값을 반영하지 않는지 확인한다.
- 실제 키 대신 가짜 키로 로그 노출 방지와 잘못된 설정 차단을 검증한다. 비밀 검사 결과도 값 대신 파일·위치·존재 여부만 보고한다. 보호된 비밀 저장소를 검사 목적으로 덤프하지 않는다.
- 운영 확인에서는 기존 승인 범위를 지키며 허위 방문/입금/광고/심사 기록을 남기지 않는다. DB 검증용 쓰기는 격리하거나 전부 롤백하고 원본 보존을 확인한다.
- 자동 승인 검토가 위험한 방식을 거절하면 우회 실행하지 않는다. 비밀값 노출이나 권한 확대가 없는 더 안전한 대안을 검토하고, 해결되지 않은 차단은 동작·이유·필요한 승인을 사용자에게 설명한다.

## 노출 발생 시와 완료 판정
- 추가 노출을 멈추고 원인을 제거한다. 원문을 다시 복사·출력하지 않으며 종류·시각·기록 위치·접근 범위만 필요한 수준으로 기록한다.
- 새 키 전환 → 연결 검증 → 기존 키 폐기/무효화, 기존 로그의 접근/보관/외부 전송 범위 확인과 정리를 별도로 추적한다. 다른 연결이나 로그인에 영향을 줄 수 있는 조치는 승인 범위를 먼저 확인한다.
- 기능 복구, 새 로그의 비밀값 차단, 기존 키 교체·무효화, 기존 로그 조사/정리를 구분해 보고한다. 미수행 항목을 완료로 표시하거나 외부 유출/피해가 없다고 단정하지 않는다.
- 현재 P0-10은 기존 인증키 교체·기존 진단 로그 접근/보관 확인이 남은 상태다. 원칙 문서 추가·배포는 이 후속 조치의 완료나 신규 키/Google 설정 변경 승인을 의미하지 않는다.
