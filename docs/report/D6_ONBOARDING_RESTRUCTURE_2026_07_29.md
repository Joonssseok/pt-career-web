지시서는 "프로필 사진 업로드가 완전히 미구현"이라고 전제했고 이를 최우선 작업으로 지시했습니다. 그러나 코드를 직접 확인한 결과 `app/expert/onboarding/profile/page.tsx`에 이미 완전히 동작하는 업로드 로직(Supabase Storage 업로드, 파일 타입/크기 검증, 실시간 미리보기)이 있었고, 로컬 실계정으로 실제 업로드→Storage 반영→에러 케이스(허용 안 된 확장자)까지 전부 재현해 정상 동작함을 확인했습니다. **이 부분은 추가 작업이 필요 없어 손대지 않았습니다.** (작업 중반에 이미 1회 별도 보고드렸습니다.)

지시서 0절의 나머지 5개 사실관계(자격증/교육 이력 명칭 혼동, `app/actions/education.ts` 부재, 근무기관 주소/전화 입력수단 부재, 회원가입 약관동의 부재, 커스텀 404 부재)는 모두 코드 확인으로 사실과 일치했습니다.

## 1. 신규 6단계 온보딩 순서 및 근거

Figma의 각 화면에 실제로 박혀 있는 "N / 6" 스텝 카운터를 근거로 순서를 확정했습니다: 경력(2/6)과 근무기관(5/6) 사이에 교육이력(3/6, "선택 항목" 배지)과 정체불명의 4번 자리가 있었고, 근무기관이 5/6이라는 것은 4번 자리가 비어있다는 뜻이었습니다. 자격·면허(레거시 `/expert/onboarding/education`, 실제로는 licenses 테이블)를 이 4번 자리로 옮기는 것이 Figma가 이미 설계해둔 자리를 채우는 가장 근거 있는 배치라고 판단했습니다.

**최종 순서**: 기본정보(1) → 경력(2) → 교육이력·신규(3, 선택) → 자격·면허·이동(4) → 근무기관(5) → 전문분야(6) → 프로필 미리보기·신규 → 제출확인(기존 D3, 변경 없음).

## 3. 근무기관 — 주소/전화/좌표

`workplaces` 테이블에 `address`/`address_detail`/`phone`/`latitude`/`longitude` 컬럼은 이미 존재했습니다(과거 라운드에서 스키마만 추가되고 UI 입력 수단이 없던 상태). 카카오/네이버 지도 API 키가 코드베이스/환경변수 어디에도 없음을 확인했으므로, 지시서가 명시적으로 허용한 대로 지오코딩 없이 **주소 텍스트 입력 + 위도/경도 수동 입력(선택)**으로 구현했습니다. "주소 검색"/지도 클릭 같은 실제로 동작하지 않는 장식용 버튼은 만들지 않았습니다(실제로 동작 안 하는 UI를 노출하는 것은 지양). `saveWorkplace()`/`getOwnWorkplace()` 서버 액션에 5개 필드 파라미터 추가.

## 4. 프로필 미리보기 — 민감정보 비노출 + 위치비공개 유지

Figma 312:2141 기준, `getOwnProfile`/`getOwnExperiences`/`getOwnEducations`/`getOwnCertifications`/`getOwnWorkplace`/`getOwnSelectedSpecialtyIds`를 조합해 자기 자신의 미승인 데이터로 미리보기를 구성했습니다. `getOwnCertifications()`는 애초에 `license_number_encrypted`/`document_path_private`를 반환하지 않으므로 별도 필터링 없이도 번호/증빙파일이 노출될 수 없는 구조입니다. 근무기관 섹션은 실제 공개 뷰(`public_expert_detail`)와 동일하게 **`is_location_public`이 꺼져 있으면 통째로 렌더링하지 않도록** 게이트를 걸었습니다(실측 결과는 6-2절).

## 5. 회원가입 약관 동의 — 기존 PR #24와의 충돌 발견 및 재조정

작업 중, 이미 구현되어 있었지만 **병합되지 않은 채 열려 있던 PR #24**(`feat/terms-privacy-consent` — `/terms`/`/privacy` 페이지, `profiles.terms_agreed_at` 컬럼, `agreeToTerms()` 액션, "온보딩 시작 화면" 동의 게이트)를 발견했습니다. 지시서는 Figma 299:440을 근거로 체크박스를 **회원가입 화면 자체**에 두라고 했는데, PR #24는 온보딩 시작 화면에 게이트를 두는 다른 방식이었습니다. CTO께 확인 후 다음 순서로 처리했습니다:

1. PR #24를 그대로 병합(`origin/main`과의 충돌 1건 — `app/layout.tsx`의 `<head>` 인라인 스타일 vs Tailwind 수정본 충돌 — 해결 후 병합).
2. `/signup`에 필수 약관 동의 체크박스 신규 추가(미체크 시 Google/이메일 가입 버튼 모두 비활성화).
3. 체크박스 자체는 새 매커니즘을 만들지 않고 **PR #24의 `agreeToTerms()`를 재사용** — 이메일 가입 시 로컬 autoconfirm처럼 세션이 즉시 생기는 경우 바로 호출, 이메일 확인이 필요한 프로덕션 흐름에서는 세션이 아직 없으므로 온보딩 시작 화면의 기존 게이트가 그대로 백업 역할을 함(중복 게이트지만 이중 안전장치로 판단, 별도 DB 쓰기 경로를 추가하지 않아 리스크 없음).

## 6. 검증 (실제 로컬 계정, mock 없음)

### 6-1. 신규 계정으로 전체 온보딩 완주
`d6-e2e-flow@test.local` 계정으로 회원가입(체크박스 게이트 확인: 미체크 시 버튼 disabled → 체크 후 활성화)부터 시작해 실제 브라우저로 전 구간 완주:
사진 업로드 → 경력(건너뜀) → 교육이력(건너뛰기 버튼으로 스킵) → 자격·면허(ISSA CPT 1건 추가) → 근무기관(주소/전화/좌표 입력, **`is_location_public` 미체크 상태로 진행**) → 전문분야(1개 선택) → 프로필 미리보기 → 제출 확인 → 제출.

각 단계 진입 시 step indicator("1/6"~"6/6")가 정확히 표시됨을 확인. 제출 후 `/my`에서 "현재 관리자 검토 중입니다" + 입력한 이름/직군/근무기관/전문분야/자격증 1건이 정확히 반영됨을 확인.

### 6-2. 프로필 미리보기 — 민감정보 비노출 + 위치비공개 유지 실측
미리보기 화면에서: 자격 및 교육 카드에 "ISSA CPT · ISSA"만 표시(자격번호/증빙파일 링크 없음) 확인. "프로필 공유"/"센터 정보 보기" 버튼이 실제로 `disabled=true`임을 JS로 확인. **근무기관 섹션 자체가 렌더링되지 않음을 확인**(`is_location_public=false`로 두었으므로) — 신규로 추가한 주소/전화/좌표 필드도 기존 정책과 동일하게 비공개 유지됨을 실증.

### 6-3. 404 페이지
실제로 존재하지 않는 경로(`/this-route-does-not-exist`) 접속 → "404 / 페이지를 찾을 수 없습니다 / 요청하신 페이지가 없거나 주소가 변경되었습니다 / 홈으로 돌아가기" 정상 노출 확인.
