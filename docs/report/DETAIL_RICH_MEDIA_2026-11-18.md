# 상세소개 서식·사진·GIF·동영상 · 2026-11-18

상태: 로컬 실제 작성창과 서버 저장 연결 완료. 운영 앱 배포·커밋·푸시·병합·현황판 게시는 하지 않음.

## 요청과 동작

- 사용자가 상세소개에 기존 공식 편집기와 사진/GIF/동영상을 요청했고, 동영상 방식은 “동영상 파일 업로드 + 유튜브 링크”로 선택했다.
- 프로필 작성 3단계에 Tiptap 공식 Simple Editor를 재사용한다. 글/서식/사진/GIF/동영상/유튜브를 하나의 문서에 배치하고 콘텐츠 블록을 이동·삭제·실행 취소할 수 있다.
- 파일은 JPEG/PNG/WebP/GIF/MP4/WebM, 1개당 20MiB·20개·기존 전용 공간 200MiB 한도를 사용한다. GIF와 영상은 변환 없이 원본 바이트를 저장한다.
- 동영상은 controls/playsInline/preload=metadata로 표시하며 자동 재생하지 않는다. 권한 검사 후 내려주는 기존 프록시에 단일 HTTP Range(206/416) 처리를 추가했다. 프록시는 한 번 요청할 때 기존 SDK로 최대20MiB 원본을 내려받은 뒤 범위를 잘라 응답한다.
- 유튜브는 공식 도메인의 HTTPS 영상 링크에서 11자 영상 ID만 추출해 저장한다. 방문자가 재생 버튼을 누를 때 youtube-nocookie.com의 고정 embed 주소에 연결하며, 임의 iframe/외부 이미지 주소는 저장하지 않는다.
- 글·서식·배치는 draft_content.detailDocument에 저장한다. 파일은 기존 private profile-detail-images 버킷과 첨부파일 목록을 재사용한다. 저장은 초안에만 반영하며 게시할 때 공개 스냅샷을 만든다.
- 기존 이미지뿐인 상세소개는 처음 편집할 때 문서의 이미지 블록으로 읽으며, 조회만으로 저장하지 않는다.
- 편집 중 파일 목록을 유지해 삭제 후 실행 취소가 가능하다. 저장/업로드/게시에는 현재 문서가 참조하는 파일만 순서대로 포함한다. 블록 삭제는 원본 파일의 영구 삭제가 아니다.

## 보안과 DB

- 적용 이력: 20261118123253_detail_rich_media. 함수/저장 형식은 기존 소개 서식과 일반 프로필을 계속 허용한다.
- 문서는 정해진 글 서식과 root 미디어 블록만 허용하며 5000자/100KB/2500노드/깊이 한도를 유지한다. 파일은 UUID+MIME, 유튜브는 영상 ID만 저장한다. blob/외부 src/임의 HTML/CSS/스크립트/iframe은 거절한다.
- 실제 저장 함수는 본인 소유·업로드 완료·미삭제 파일과 MIME이 일치하는지 검사한다. 첨부 포함 저장은 문서가 참조하는 파일을 같은 첨부 목록에 포함해야 한다.
- 게시 트리거는 공개될 문서의 파일이 본인의 초안 첨부 목록에 있는지 확인한다. 공개 함수는 게시된 문서만 반환하고 초안은 반환하지 않는다.
- private 버킷과 RLS·소유자/공개 판정·변경 충돌 검사·파일 크기/총량 한도는 유지했다. 버킷의 허용 MIME과 파일 MIME 제약만 필요한 형식으로 확장했다.
- 기존 3개 프로필 버전/첨부 행/업로드 행은 적용과 검증 전후 지문이 동일하다. 시험 프로필/파일을 운영에 추가하거나 기존 자료를 수정하지 않았다.
- 보안 advisor의 기존 지적 종류와 개수는 변경 전후 동일하다. 기존 보안 후속 항목을 완료로 처리하지 않았다.

## 확인

- TypeScript 통과, 전체 자동 검사 79묶음/595항목 통과(기존 로컬 Supabase 전용 통합 묶음 6개 제외).
- 별도 PGlite에서 실제 변경 SQL 생성 및 저장/게시 함수 실행, 기존 자료 호환, 안전 형식/금지 형식, 파일 소유·MIME·첨부 참조, 공개 전 초안 보호, 게시 시 누락 파일 차단 등 26개 검사 통과.
- 실제 연결 DB에서 기존 본인 초안에 상세 글/서식/유튜브 문서를 트랜잭션 안에서 저장→재조회했다. 공개 결과에 초안이 없고 첨부 revision 충돌이 차단됨을 확인한 후 모두 롤백했다.
- 쓰기 없는 독립 미리보기에서 시험 PNG/2프레임 GIF/1초 MP4 파일을 선택해 표시했다. 이미지 naturalWidth=480, 영상 duration=1·readyState=4 확인. 첨부 삭제→Undo 복원, 유튜브 영상 ID 입력, 클릭 전 iframe=0 확인.
- 실제 상세소개 작성창의 공식 툴바·파일/유튜브 버튼을 확인했다. 모바일375 폭에서 문서360·삽입 도구286으로 가로 넘침 없음.
- 새 페이지 초기 조회/단계 이동 후 운영 프로필/파일 데이터가 변하지 않은 것을 확인했다. 시험 글과 파일은 운영으로 전송하지 않았다.

## 남은 검증과 복구

- 사용자의 실제 파일로 운영 업로드/실제 게시하는 시험, 실기기 코덱별 재생, 장시간/고화질 영상 부하 검증은 하지 않았다. 20MiB를 넘는 영상은 유튜브 링크를 사용할 수 있다.
- 운영 앱 배포 전에는 운영 사이트가 새 상세소개 문서를 표시하지 않는다. 로컬 실제 작성창은 연결된 서버 초안에 저장된다.
- 복구는 앱을 이전 화면으로 되돌리는 방식이다. 저장된 새 문서/미디어를 삭제하지 않으며, GIF/영상이 저장된 뒤에는 DB 허용 형식 제약을 무조건 이전 형식으로 좁히지 않는다.
- 기존 전용 공간의 사용하지 않는 파일 정리는 기존 본인 선택/참조 검사 절차를 유지한다.
